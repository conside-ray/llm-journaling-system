# AGENTS.md

## Purpose

This repository is a local-first, AI-assisted journaling and reflection system.

Its goal is to help transform raw journal entries into:
- useful weekly and monthly reviews
- durable insights, ideas, and principles
- better self-understanding and better decisions over time

The system is designed to reduce the friction of reflection, especially the friction of reviewing, distilling, and carrying forward what matters.

The human provides the raw journals and the core context.
The agent helps compile, synthesize, and propose durable learnings.
The human remains the final judge of meaning, priorities, and promotion.

---

## Core Principles

1. **Reduce friction, do not add bureaucracy.**  
   The system should make reflection easier and more useful, not more ceremonial or complex.

2. **Preserve human judgment.**  
   The agent may summarize, compare, and propose. It must not silently redefine the user’s priorities, projects, areas, or self-model.

3. **Prefer evidence over eloquence.**  
   Strong outputs are grounded in repeated signals, concrete examples, and observed patterns — not vague motivational language.

4. **Optimize for reuse.**  
   Good outputs should help future planning, decision-making, or pattern recognition.

5. **Be conservative with durable memory.**  
   Promotion should be selective. Not every interesting thought deserves to become a durable insight or principle.

6. **Treat context as stable unless explicitly changed by the human.**  
   The /context directory defines important reference files and should not be casually rewritten by the agent.

## Directory Roles and Ownership

### /journals
Contains time-based records and compilations.

- `journals/daily/`: human-written daily journals.
- `journals/weekly/`: AI-drafted weekly reviews, human-reviewed. Any new weekly review files generated by the agent should be placed in this directory. 
- `journals/monthly/`: AI-drafted monthly reviews, human-reviewed. Any new monthly review files generated by the agent should be placed in this directory. 

### /context
Contains stable human-owned context for the agent to understand different aspects of the human's life, work, and priorities.

- `context/projects/`: project notes
- `context/areas/`: area notes
- `context/notes/`: selective supporting notes that may contain reusable reasoning, discussions, or reference material linked from journals or relevant to active projects/areas
- `context/priorities.md`: current priorities across time horizons

These files are authoritative context inputs.  
They may be read by the agent, but they should not be modified during normal weekly or monthly compilation runs.

### /promotion
Contains durable memory files and promotion staging.

- `promotion/candidates.md`: AI-generated staging file for reviewable promotion candidates
- `promotion/insights.md`: approved durable insights
- `promotion/ideas.md`: approved durable ideas
- `promotion/principles.md`: approved operating principles

`promotion/candidates.md` is agent-writable.  
The other promotion files are canonical and should only be updated after human review and approval.

### /templates
Contains templates used to create new files.

- `templates/Area Template.md`: The template for any area to be created. Mainly used by human. 
- `templates/Project Template.md`: The template for any project to be created. Mainly used by human.
- `templates/Daily Journal @yyyy-mm-dd.md`: The template for daily journals to be created. Mainly used by human.
- `Weekly Review @yyyy-ww.md`: The template for weekly reviews to be created. The agent should use it as the basis for any weekly compilation run. 
- `Monthly Review @yyyy-mm.md`: The template for monthly reviews to be created. The agent should use it as the basis for any monthly compilation run. 

### /system
Contains agent-facing instructions and skills.

- `system/AGENTS.md`: repository-wide agent rules
- `system/skills/`: task-specific skills and procedures

## Standard Workflows

### 1. Daily journaling
The human writes daily journal entries in `journals/daily/`.

These are the raw inputs for later compilation.

### 2. Weekly compilation
The weekly workflow has two output streams:

1. Draft a weekly review in `journals/weekly/`
2. Generate or update reviewable promotion candidates in `promotion/candidates.md`

The weekly run should read:
- the relevant daily journals for the week
- `context/priorities.md`
- relevant project files referenced in the week
- relevant area files when useful
- relevant note files referenced in the week
- prior weekly review if needed

The weekly run should not directly modify canonical promotion files or context files.

### 3. Monthly compilation
The monthly workflow drafts a monthly review in `journals/monthly/`.

It should primarily use:
- the month’s weekly reviews
- `context/priorities.md`
- relevant project files
- relevant area files
- relevant note files
- promotion files when useful for higher-confidence pattern recognition

### 4. Promotion review and application
Promotion is a separate workflow from compilation.

The normal order is:
1. The agent proposes candidates in `promotion/candidates.md`
2. The human reviews and marks decisions
3. Approved candidates are applied to `promotion/insights.md`, `promotion/ideas.md`, or `promotion/principles.md`

The agent must not directly apply promotions unless explicitly instructed to do so after review.

## Update Policy by File Type

### Agent may create or update:
- weekly review drafts
- monthly review drafts
- `promotion/candidates.md`

### Agent may read but not normally modify:
- daily journals
- project files
- area files
- note files
- `context/priorities.md`
- canonical promotion files (`insights.md`, `ideas.md`, `principles.md`)

### Agent may suggest updates to:
- project files
- area files
- `priorities.md`
- canonical promotion files

But such suggestions should be surfaced explicitly, not silently applied during normal compilation runs.

---

## Promotion Policy

Promotion is review-gated.

The agent should treat `promotion/candidates.md` as a staging queue, not as durable memory.

When proposing promotion candidates, the agent should:
- group candidates by type
- state why each candidate matters
- include evidence
- suggest a destination
- indicate confidence
- avoid promoting weak, one-off, or vague observations

The canonical promotion files should remain selective, compact, and useful.

---

## Quality Standards

When generating reviews or promotion candidates, the agent should:

- identify what actually mattered, not just what appeared in the notes
- distinguish real progress from fake progress
- compare stated priorities against actual behavior
- surface repeated frictions, drifts, and bottlenecks
- avoid generic motivational language
- avoid overstating confidence
- avoid treating one bad day or one unusual week as a durable truth
- prefer concise, readable, diagnostic writing over decorative writing

The best outputs should feel like a clear memo, not like therapy theater or productivity fluff.

## Skill Usage Rules

Use task-specific skills from `system/skills/` when available.

Expected core skills include:
- weekly compilation
- monthly compilation
- promotion candidate generation
- promotion application
- file maintenance or consolidation (optional later)

Global rules in `AGENTS.md` apply to all workflows.
Task-specific output formats and procedures should be defined in the relevant skill files.

If there is a conflict:
1. explicit human instruction overrides default workflow
2. task-specific skill rules override generic style assumptions
3. `AGENTS.md` governs repository-wide boundaries and file ownership

---

## Future Evolution

This system should stay lightweight in v1.

Do not introduce additional complexity such as advanced retrieval layers, automatic context rewriting, or aggressive memory mutation unless the current workflow proves useful and sustainable first.

Prefer a system that survives imperfect weeks over a system that is theoretically elegant but fragile in practice.
